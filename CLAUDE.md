## Architecture

### Cloud model (the thing to understand first)

Several devices (a PC and a phone, say) share the same live data through the internet:

- **Supabase Postgres is the source of truth** (`supabase/migrations`). Each table mirrors a Dexie table: a primary-key column plus `data jsonb` holding the whole row exactly as its type in `src/types/` defines it. Triggers do the bookkeeping: `sync_row` copies the key into `data` (so an insert comes back carrying its generated id) and stamps `updated_at`; `log_deletion` records deletes in `deletions`. `sync_meta.epoch` is bumped when data is rewritten wholesale (a migration that moves fields between tables does it, as the permissions one did), which makes every device drop its mirror and pull everything again.
- **Reads go straight from the browser to Supabase.** `src/sync/index.ts` keeps the Dexie mirror current: on every (re)connect it pulls the rows whose `updated_at` passed its per-table cursor (all of them the first time), replays `deletions`, then applies Realtime `postgres_changes` as they arrive. `pull()` runs twice (the second pass is incremental and nearly free) so a Realtime change that landed during the first download is not left overwritten by that older snapshot. `src/db/repositories/*.ts` read Dexie only, through `useLiveQuery`, so the app keeps showing the last known data offline (and keeps selling: see "Selling without internet" below).
- **Writes go through the API** (`server/`, Express): `src/api/client.ts` (`apiPost`/`apiPut`/`apiDelete`) sends the Supabase session as a Bearer token, and a repository never writes Dexie itself (Realtime brings the result back). The API runs as the Firebase Function `api` (`functions/index.js`, region us-east4, next to the database) behind the Hosting rewrite `/api/**`; locally it's `npm run server`, with Vite proxying `/api`. It connects through the Supabase session pooler with certificate verification (`server/supabaseCa.ts`) — the direct `db.<ref>.supabase.co` host is IPv6-only.
- **Who can do what:** every person signs in with **their own** Supabase Auth account (email + password) — the owner's, or the one an administrator gave them in Configuración → Usuarios. `public.is_staff()` (RLS) and `server/auth.ts` (which verifies the token with `/auth/v1/user`, then `checkAccount` in `server/domain/counter.ts`) accept an email that is in `public.staff` (an **owner**: always Administrador; add one with `insert into public.staff (email, name) values (...)`; the owner's display name is `settings.owner.name`, else that row's `name`, else "Propietario" — and when the owner's account email changes in Supabase Auth, `public.staff.email` must be changed to match **by hand in the SQL editor** (`update public.staff set email = '…', name = '…' where email = '…'`), or nobody can sign in as owner) or the `email` of an **active** `usuarios` row (that user, with their role). Neither reads nor writes work without it; browsers can never write tables directly (only SELECT is granted). There is no "store account" shared by every device any more: who signed in *is* who works, until they sign out ("Cambiar de usuario" = sign out, the next person enters with their own account; the local data stays on the device unless "Cerrar sesión y borrar").
- **Permissions are enforced by the server and the database, not the screen** (migrations `20261005000000_permisos_servidor.sql` and `20261007000000_cuentas_por_persona.sql`, logic in `server/domain/counter.ts`). `POST /api/counter/session` (the app calls it as it starts and every minute) binds the device's Supabase session to the person whose account it is (`private.counter_sessions`, keyed by the JWT's `session_id`, with their role's permissions; renewed by that call, 12 h of slack) — nobody can bind themselves to someone else: the person comes from the verified token's email, never from the request. Every route calls `requireNeed(q, actor, need)` (the operator's permissions, else an approval in `private.approvals` — someone allowed typed their PIN on that session; sale approvals are spent by the sale) and signs the work with the operator's name (`Ana (autorizó Sofía)` when an approval was used). **PINs only authorize**, they no longer sign anyone in: `POST /api/counter/approve` checks one against `private.pins` (HMAC with a pepper that never leaves the database; no browser can read the `private` schema), with lockouts per device (5 wrong → 30 s, doubling) and store-wide (30 in 24 h → 1 h); the owner's master PIN refuses to authorize while it is still the factory `1234`. A user's PIN is optional. `private.account_policy.sessions_since` makes any session that typed its password before the switch answer 401 `{ reauth: true }` (the app signs out and shows the login). Secret fields never stay in the rows every device reads: triggers move a product's `cost` to `productCosts`, a sale's `ganancia`/item costs and a cierre's `totalGanancia` to `profits`, PIN hashes to `private.pins` — so any code may keep writing whole objects. RLS serves those tables (and `cashMovements`, `cashSessions`, `cierres`, `purchaseOrders`, `payables`, `suppliers`) only through `public.has_perm(perm)`, i.e. to a session that the server bound to someone allowed (`private.access_state`, the old "open counter", is empty and unused); `cajaState` (caja open or not, no amounts) is what everyone gets. `refreshCounterPerms` keeps every bound session's permissions in step whenever roles or a user change (and at startup; a deactivated user's sessions lose everything). The sale route re-prices every line from the inventory and only accepts a manual discount, a changed total or fiado with `ventas.*` permission or approval; it sells only inventory products (the old "producto libre" was removed — `CartItem.isFree` survives only for the `CORR` line of a sale correction and for old sales, whose receipts still tag it `[Libre]`). Emergency undos: `supabase/rollback/20261005000000_permisos_servidor.down.sql` (it can't restore PINs: the owner's goes back to 1234) and `supabase/rollback/20261007000000_cuentas_por_persona.down.sql` (only the owner's account opens the app again).
- **Accounts are created by the API, not the browser** (`server/accounts.ts`, injected into `createApp(db, auth, accounts)`): `server/domain/users.ts` creates/updates/deletes the Supabase Auth account of each user with the project's **secret key** (`SUPABASE_SECRET_KEY`: `.env.local` locally, Secret Manager for the Function) through the Auth admin API, after every rule passed and the database write is done (it isn't part of the transaction; a rejected password puts a changed email back). Without the key (`accounts.enabled` false) the app only records each user's email and the account is made in the Supabase dashboard (Authentication → Users → Add user, "Auto Confirm User"). Users can change their own password (`supabase.auth.updateUser`); an administrator can't deactivate, delete or demote themselves. The project keeps public sign-ups off (`disable_signup`, checked with `GET /auth/v1/settings`) and email confirmation on — keep it that way: an account is trusted by its email. **Profile pictures** (a user's `usuarios.photo`, the owner's `settings.owner.photo`, both next to the name; set by the Administrador in Configuración → Usuarios): the browser squares and shrinks the picked image to a ~256 px JPEG data URL (`src/shared/lib/image.ts`), kept inline in the row so it syncs like any other field; `src/shared/lib/photo.ts` (`cleanPhoto`) is the one rule — JPEG only, ≤ 60 000 characters, never SVG or a URL — and the server (`checkPhoto` in `server/domain/users.ts`, also for `PUT /api/settings` `owner`) refuses anything else. `Avatar` (`src/shared/components/Avatar.tsx`) draws the picture or the initials.
- **Money logic lives in `server/domain/`** (`cash.ts`, `purchasing.ts`, `cierre.ts`, `sales.ts`; `counter.ts` and `users.ts` for who may do what; `secrets.ts` reads costs and profits): plain async functions `(q, input)` that run inside the caller's `db.tx`, so a rejected operation changes nothing. The connection a transaction holds keeps an `'error'` listener (`pgDb` in `server/db.ts`): the pool's own one is off it while it is checked out, and a drop between two queries — the internet blinking — would otherwise be an unhandled event that ends the whole API process (it did, locally); the next query rejects instead and the dropped connection is discarded. `db.tx` (`server/db.ts`) takes one app-wide `pg_advisory_xact_lock` first, so writes run one at a time — the guarantee the old synchronous SQLite server had — and a stock or balance check can't be raced by another device. Every route goes through `handle()` (`server/routes/http.ts`), because Express 4 doesn't catch rejected promises. **What makes a save slow is the number of round trips to the database, not the work**: from a developer's computer (the local API talks to the cloud database) each costs ~170 ms, so a route is judged by `queries + 2` (`db.tx` sends BEGIN and the lock together, then COMMIT). Keep them few: who is asking and the settings (roles, owner name) come from ONE query (`accountOf` in `server/domain/counter.ts`, shared by `actorOf`/`checkAccount`); never loop `getRow`/`putRow`/`insertAutoRow` over products — read them with `getRowsByKey`, do the arithmetic in JS and write with `putRows` / `setStocks` / `insertAutoRows` (`server/routes/generic.ts`), as sales, `receiveOrder`, bulk entries and the cyclic count do (a sale of any size is 7 queries; it used to be 3 per line). Whatever still loops over rows inside one `db.tx` (the import: ~2 queries per row) holds the lock and has to finish inside the Function's 60 s, or nobody can sell meanwhile: imports stop at 3,000 rows (`MAX_IMPORT_ROWS`), the cyclic count and bulk entries (batched, so cheap) at 5,000, and the calls to Supabase Auth made inside a transaction (`server/accounts.ts`) time out at 8 s. Shared request helpers (`text`, `roundQty`, `errorMessage`…) live in `server/routes/generic.ts`.
- Adding a new entity touches:
  - the type in `src/types/`;
  - a **new** migration in `supabase/migrations` (table with `data jsonb` + `updated_at`, both triggers, RLS policy — `is_staff()` for what everyone may see, `has_perm('…')` for a secret one — privileges: `revoke all` + `grant select to authenticated`, `supabase_realtime` publication) applied with `npm run db:push`;
  - the Dexie schema in `src/db/schema.ts` as a **new** `this.version(n+1).stores({...})` block (never edit an earlier one; `null` drops a table);
  - the route in `server/routes/*.ts`, mounted in `server/app.ts`;
  - the repository's read/write split;
  - `TABLES` in `src/sync/index.ts`, which must list every synced table — or, for a secret one, `SECURE_TABLES` in `src/db/secure.ts` (with the permission its RLS policy asks) instead of Dexie;
  - the permission check in its route (`requireNeed`).

  A plain new field on an existing entity needs none of that schema work — Dexie only declares *indexed* fields and Postgres keeps the row as `data` — only a new index or table does.
- The Rutas module was removed from the app (Dexie v5 drops its local table), but `supabase/migrations/20261004000000_route_orders.sql` and the `routeOrders` table remain in the database: nothing reads or writes it, and dropping it is the user's call (a new migration, never an edit of the old one).
- The default `Settings` row exists twice and the two copies must stay identical: the seed in the first migration and the `getSettings()` fallback in `src/db/repositories/settings.ts`. The seed's `pinHash` (factory PIN `1234`) was moved to `private.pins` by the permissions migration; the master PIN authorizes nothing until changed, and Configuración shows a red warning while it is the factory one (`GET /api/counter/security`). `roles`, `access` (now only `idleSignOutMinutes`, see `sanitizeAccess`; older `mode`/`counterRole`/`autoLockMinutes` are dropped when read) and `business` are optional on purpose (absent = defaults), so neither copy needs them. `PUT /api/settings` goes through `applySettingsPatch` (`server/domain/users.ts`): the theme from anyone, `storeName`/`business`/`roles`/`access`/`hidScannerEnabled` from the Administrador only, anything else refused; it cleans `roles`/`access` and refuses removing a role someone has. The master PIN changes through `/api/counter/owner-pin` (Administrador; it needs no old PIN and lifts every PIN lockout, which replaces the old "recover with the account password" route); `lastCajero`/`cajaBase` are written by the Cierre Z.

### Selling without internet (`src/offline`, `server/domain/offlineSales.ts`)

The till must keep selling — and taking stock off the shelf — when the internet goes. A sale is a *fact* (the goods left, the customer paid), so without internet it is never refused.

- **Reaching the server.** `src/api/client.ts` throws `NetworkError` (`timedOut`; `noSession` when the access token couldn't be renewed offline) when nothing answers, and every call has a time limit (60 s by default, `{ timeoutMs }` per call) that covers the session lookup — `supabase.auth.getSession()` keeps retrying a token refresh for up to 30 s without internet — and the reading of the answer's body, not just the headers. `isServerTrouble(err)` = `NetworkError` or HTTP ≥ 500. Calls report to `useConnectionStore.reachable` (false after a `NetworkError` that isn't `noSession`, or an answer that says the server is down — `serverDown` in `client.ts`: a 502/503/504 that isn't JSON, i.e. a gateway's page, or that carries `down: true`, which `handle()` adds to its database-unreachable 503; the API's own 502/503 for "no mail account", "Supabase refused the account"… are not an outage and must not look like one); `src/offline/connection.ts` also probes `/api/health` (it must answer JSON `{ ok: true }`, not a Wi-Fi login page) every 10 s while down, every 60 s otherwise, and on the `online`/`offline`/visibility events. A `NetworkError`/`ApiError` nobody caught is shown as a toast by `AppShell` instead of failing silently.
- **Charging** (`sell()` in `useFinalizeSale.ts`): the cart gets a `clientId` (UUID, `newClientId()`) and goes to `/api/sales/finalize` first (10 s patience) when the server is thought reachable; on `isServerTrouble` — or straight away when it is known to be down — `saveSaleOffline` keeps it. A refusal (stock, permission…) is shown and never kept. Sending the same `clientId` twice is harmless: the server answers the repeat with the sale it already has (`saleByClientId`; the unique index `sales_client_id` of migration `20261013000000_ventas_sin_internet.sql` is the safety net under that check).
- **What is kept** (`src/offline/outbox.ts`, Dexie v7 table `outbox`, on the device only): one `OutboxSale` per sale — the payload the server reads (`OfflineSalePayload`), `status` `pending`/`rejected`, attempts, last error. The lists show a *provisional sale*: a `sales` row with a NEGATIVE id `-seq` and `pendingSync: true`, printed `PEND-0003` (`formatSaleId`, `isPendingSaleId`; receipt headed "RECIBO PROVISIONAL"; no Correo/WhatsApp, no Corregir, no fiado payments until it is sent). **Stock overlay**: a product's local `stock` is the server's figure minus what pending sales took (never below 0), and `Product.serverStock` (local only) holds the server's own figure while anything is held back — so the cart's stock cap, the low-stock badges and Stock are right offline. Everything that touches `outbox` and `products` runs in one Dexie transaction: `saveSaleOffline`, `settleSale`, `rejectSale`/`retrySale`/`discardSale` (through `restock`), and the sync's writes — `holdBack` on server products, `reconcileSales` on server sales (a server sale whose `clientId` is in the outbox settles it — its own sale whose answer got lost — and a full download, which empties `sales`, gets the provisional rows put back).
- **Sending** (`src/offline/outboxSync.ts`, started by `startOffline()` from `AppShell`): oldest first, one at a time, under a Web Lock (two tabs don't send twice), to `POST /api/sales/offline`. No answer/408/429/502–504 → stop and retry later (the wait grows to 60 s; the connection coming back skips it; otherwise every 15 s); 401/403 → stop until somebody signs in; any other 5xx → skip that sale for now and send the rest; other 4xx → `rejected`, which a person settles in `SyncSheet` (retry or discard). After sending, `syncNow()` re-downloads so the local figures are the server's. Before a write that adds up stock or caja (`BOOKS_WRITES` in `client.ts`: products, entradas, inventory, cierres, cash, receiving an order, paying a payable) the outbox is flushed first (`onBeforeBooksWrite`) or the write is refused with an explanation; the Cierre Z waits for it too — and for sales the server refused, which a person settles first.
- **Server** (`ingestOfflineSale`): saves the sale whatever it holds and writes what did not add up in `Sale.reviewNotes` (stock that wasn't there — left at 0 —, a price that is no longer one of the product's, a deleted product or customer, totals that don't match, a discount/total change/fiado the claimed seller couldn't authorize, a day another device already closed, an absurd date). The seller is whoever made the sale (`operatorById`: name and permissions come from the database, never from the payload), with the permissions of the two of them in common — a sale never claims more authority than whoever sends it has — and `syncedBy` whoever sent it; the caja movement carries the sale's date and goes in the workday open then (`sessionAt`). Only a payload that can't be a sale (no lines, bad payment method, bad `clientId`) is a 400. `POST /api/sales/:id/review` (`facturas.corregir`) marks the notes as read (`ReviewNotes` in the receipt, "por revisar" chip in Facturas). `handle()` answers 503 `{ down: true }` when the database can't be reached (`isDatabaseDown`), so the app can tell "server out of reach" from a broken rule.
- **Starting without internet** (`AuthGate`): when Supabase says "no session" only because the access token expired and it can't renew it, `storedSignIn()` (the `sb-<project>-auth-token` entry of localStorage, which only a real sign-out or a rejected refresh token removes) lets the person in on the local data — at once when `navigator.onLine` is false, after 4 s otherwise — and the token renews whenever the connection returns (after Supabase's 60 s pause between refresh attempts, at worst). What needs the internet by design: the first sign-in on a device, "Cambiar de usuario" (`signOut`, which refuses up front when the server can't be reached — `probeNow`, not whatever Supabase's client happens to do — and also refuses "forget this device" while sales are waiting) and PIN approvals — each person's password and every PIN are checked online.
- **Fonts** are bundled (`@fontsource/ibm-plex-*`, imported in `src/main.tsx` — not from `index.css`, where the font files' relative URLs would not be rewritten) and `woff2` is precached, so the first paint never waits for Google Fonts.
- **Installed apps** (Windows .exe, Android .apk — the shells themselves are not in the repo): build the same code with `VITE_PACKAGED=1` (relative asset paths, hash router, no service worker), `VITE_API_URL` (the API's address, e.g. `https://plastimax-fr.web.app`, which `src/api/base.ts` puts in front of every `/api` call) and `VITE_PUBLIC_URL` (the address a receipt's WhatsApp link opens). The API answers CORS (`*`: every route authenticates with a bearer token in a header, never a cookie) before it authenticates. Their offline behaviour is the same code — IndexedDB and the outbox, not the service worker.
- UI: `ConnectionPill` (nav corner: "Sin conexión", "Enviando N…", "N rechazadas") opens `SyncSheet` (what waits, what the server refused, "Enviar ahora").
- Going to production: `npm run db:backup` → `npm run db:push` (the new index) → `npm run deploy`, back to back. A new screen with the old Function still works (`/api/sales/offline` answers 404, which the outbox reads as "server not ready": the sales wait and go up once the Function is deployed); an old screen with the new Function simply never uses it.

### Deployment and secrets

- Firebase project `plastimax-fr`: Hosting serves `dist/` at https://plastimax-fr.web.app (`firebase.json`, SPA rewrite, immutable `/assets/**`, no-cache service worker) and rewrites `/api/**` to the Function. `npm run deploy` does it all, but only with the Google account that owns `plastimax-fr` signed in to the Firebase CLI (installed globally; check `firebase login:list`): another account gets a 403 on every command, and deploying the Function also needs the "Service Account User" role on `plastimax-fr@appspot.gserviceaccount.com`, or the whole deploy stops at `iam.serviceAccounts.ActAs` before publishing anything. A change to screens alone goes out with `firebase deploy --project plastimax-fr --only hosting`; anything in `server/` — or in a shared lib the API bundle imports, such as `src/shared/lib/permissions.ts` — reaches production only with the Function (until then the old server keeps running next to the new screens, which is fine as long as the change is backwards compatible).
- Secrets: the database URL (with the password) lives in `.env.local` (git-ignored, read by the local server and the db scripts) and in Secret Manager as `SUPABASE_DB_URL` for the Function (`firebase functions:secrets:set SUPABASE_DB_URL`, then redeploy the Function). The Supabase **secret key** (Project Settings → API Keys → Secret keys) is `SUPABASE_SECRET_KEY` in the same two places; the Function declares it in `functions/index.js`, so the secret must exist **before** a deploy (`firebase functions:secrets:set SUPABASE_SECRET_KEY`). Never paste either into chat or commit them. Public config: `.env` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, bundled into the app) and `functions/.env`. The publishable key is public by design.

Their public config and the web push key pair's public key are `VITE_FIREBASE_*` in `.env` (Firebase console → Configuración del proyecto → Cloud Messaging → Certificados push web; `firebase apps:sdkconfig`). The scheduled Functions need Cloud Scheduler, which the Blaze plan has.
- **E-mail for receipts** goes out through Gmail: `GMAIL_USER` (the account, `francirojas46@gmail.com`; not secret — `functions/.env` and `.env.local`) and `GMAIL_APP_PASSWORD` (its app password, never the account password; Secret Manager for the Function and `.env.local` locally). Like the other secrets, the Function declares it in `functions/index.js`, so `firebase functions:secrets:set GMAIL_APP_PASSWORD` must run **before** the next Function deploy or the whole deploy stops. Without them the server answers 503 "correo no configurado" and everything else works. The sender name is the store name from Configuración → Negocio.
- A migration that changes what the deployed API or app expects goes out as `npm run db:backup` → `npm run db:push` → `npm run deploy`, back to back (in between, the running version may misbehave); open devices pick up the new version by themselves: `startAppUpdate` (`src/app/appUpdate.ts`, started from `App.tsx`) registers the service worker — `skipWaiting` + `clientsClaim` in `vite.config.ts`, so a new version takes control as soon as it is installed — asks for a newer one every 5 minutes (and when the app comes to the front or the internet returns) and, once one has taken over, restarts the page: at once if nothing is in progress, otherwise (a cart with products — carts live in memory —, a sheet open, a save in flight) it says "Hay una versión nueva" and waits, looking every 10 s, until the sale is done. A device running a build from before this existed updates the next time it is opened or reloaded. The installed .exe/.apk (no service worker) are updated by installing a new build. The one-account-per-person switch also signs out every session that was open before it (they sign in again, each with their own account), and needs `SUPABASE_SECRET_KEY` set as a Firebase secret first.

### Frontend structure

- `src/app/` — shell chrome: `AppShell.tsx` (layout + mounts global effects: sync, API warm-up, theme, scanner, keyboard shortcuts), `Header`/`DesktopTabs`/`BottomNav` (mobile gets the slim `Header` + `BottomNav`, `md:`+ swaps in the `DesktopTabs` top bar — one breakpoint switch, pages don't special-case it), `navConfig.ts` (single source of nav items + live badge counts, shared by both chromes: Stock = low-stock products, Fiados = debtors with a balance, Proveedores = accounts payable still unpaid, overdue or not).
- `src/features/auth/` — `AuthGate` (wraps the router in `App.tsx`: nothing loads until someone who works at the store signs in with their own account; an account that isn't the store's is signed straight back out, and `onSignedOut` sends the next person to Venta), `LoginPage` (email + password), `session.ts` (`signOut()` — "Cambiar de usuario": ends the server binding, `supabase.auth.signOut({ scope: 'local' })` so the same account on another device stays in, stops sync and drops the in-memory secret data; `{ forget: true }` also wipes the local copy — plus the shared "last activity" stamp for the inactivity sign-out), `useChangeUser`, `ChangePasswordModal` (own password), `useAccountEmail` and `useProfilePhoto` (the picture of whoever is working).
- `src/features/settings/` — Configuración (Administrador only): one section at a time from a side menu, kept in the URL as `?seccion=` — `negocio` (store name and the receipt details in `settings.business`, printed by `PrintHeader`/`ReceiptSheet`), `usuarios` (the owner's card — name and picture, `OwnerSheet` — and each person's email, role, picture, optional PIN and password), `roles` (draft edited locally, saved as one `settings.roles` write; "Comparar" is the role × permission matrix), `seguridad` (`settings.access.idleSignOutMinutes` and the owner's master PIN), `dispositivo` (barcode reader, shortcuts, your account: change user / forget this device). Its rows/cards/switches come from `components/ui.tsx`: reuse them for any new setting.
- `src/features/<name>/` — one folder per route/domain (`pos`, `inventory`, `customers`, `fiados`, `invoices`, `cash` for Cajas, `suppliers` for Proveedores and purchasing, `reports`, `settings`, `pin`, `auth`), each with its own `components/`, `hooks/`, and sometimes `lib/` for pure logic (e.g. `features/fiados/lib/fiadoGrouping.ts`, shared by nav badges and the Fiados page).
- `src/api/` — `supabase.ts` (the single Supabase client) and `client.ts` (the write API wrapper; a 403 carrying `need` asks for the PIN of someone allowed — `onPermissionNeeded`, set by `usePermission` — and retries once).
- `src/db/secure.ts` — the secret tables (`productCosts`, `profits`, the cash ledger, purchasing, cierres) in memory only, never IndexedDB: `useSecureTable(t)` / `useSecureLoaded(t)`, filled and emptied by `setSecurePerms` in `src/sync` as the permissions of whoever is working change. Costs and profits are merged in where shown with `src/shared/hooks/useSecretFigures.ts` (`useCostMap`/`withCosts`, `useProfits`/`withProfits`) — a synced `Product`/`Sale` never has `cost`/`ganancia`. A screen that must wait for them (an export right after signing someone in) uses `whenSecureLoaded`.
- `src/store/` — Zustand stores for ephemeral UI/client state (carts, toasts, confirm dialog, PIN prompt, who is working on this device, scanner on/off). Persisted business data goes through `src/db/`, not a store.
- **Several carts can be open at once** (customers who arrive together), shown as tabs on top of the cart card (`features/pos/components/CartTabs.tsx`; "+" opens another, the pencil / a double-click renames, "x" closes). `useCartStore` holds `carts` + `activeId`, and the `Cart` shape is in the store file; every edit action (`addUnitItem`, `setCustomer`, `clear`...) acts on the ACTIVE cart. Read a cart's data with `useActiveCart((c) => c.items)` in a component or `selectActiveCart(useCartStore.getState())` outside one — there is no top-level `items`. A completed sale closes the cart that was charged **by id** (`closeCart(cartId)`, id captured at the start of `useFinalizeSale`): the cashier can switch carts while the sale is being saved, so "the active cart" is the wrong one to clear there. Closing the last cart leaves a fresh empty one. A line's quantity can also be typed over, not only stepped with − and + (`QtyField` in `CartLine`, `setQty` in the store: whole units, it stops at the stock and says so, and an empty field or 0 changes nothing — taking a line out is the X). Carts live in memory only: a page reload empties them, same as the single cart did.
- `src/shared/` — cross-feature `components/` (e.g. `ToastHost`, `ConfirmDialog` — both driven by their Zustand stores and rendered once from `AppShell`), `hooks/`, `lib/`. Stock, Clientes, Fiados, Facturas, the three lists of Proveedores (Pedidos, Por pagar, Proveedores) and the product picker of Venta are spreadsheet-style lists on the shared virtualized `DataTable` (with `SearchInput`, `AddFab`, `Chip` and `lib/sortRows`): build any new list that way rather than as a card grid. Venta's search box has no dropdown: it narrows that same table (`buildSaleList` in `features/pos/lib/saleProducts.ts`), `Highlight` (`shared/components`) marks what was typed in yellow in the code, name and brand cells, and ↓/↑ + Enter walk the table (the page keeps the row index and passes it as `DataTable`'s `activeKey`, which outlines the row and scrolls it into view). That table is laid out like a spreadsheet — one 30 px line per product, the brand after the name, "N precios" beside the price (`dense` plus `compact`, the thinner header, on `DataTable`); the other lists keep their taller rows. Don't read the whole `sales` table into a screen (every sale that arrives re-reads it on every open device): Facturas loads only the days on screen (the `dayKey` index), Fiados, Reporte's fiado figures and the nav badge only `payMethod = 'fiado'`, Clientes only the sales that have a customer. Each keeps its row-building, filtering and sorting as pure functions in its feature's `lib/` (`invoiceRows.ts`, `fiadoRows.ts`, `orderRows.ts`, `payableRows.ts`, `supplierRows.ts`, `saleProducts.ts`…) and its columns in a `*Table` component. `SearchInput` takes a `historyKey` naming the list of that box's last ten searches (`lib/searchHistory.ts`, per device in `localStorage`; a search is recorded on Enter, on leaving the box with it typed, or on picking a suggestion, and "Cerrar sesión y borrar" wipes them): give every new list's search box its own key. Its columns have a minimum width and the table scrolls sideways only when they don't fit; two options keep a wide list on a laptop screen: `dense` (8px cell padding instead of 10px) and a `drop` number on a column — when the table (measured, `lib/fitColumns`) has less room than all the columns, the lowest numbers leave first, but only if that makes the rest fit (otherwise, on a phone, it keeps every column and scrolls). Stock uses both: with costs revealed it fits a 1366px window with no scrolling sideways, dropping Unidad, Mín., Categoría and Estado (in that order) on narrower ones. A row's `rowClassName` can't reliably set a background (it competes with the zebra `bg-s2`): mark rows with an inset shadow (`shadow-[inset_3px_0_0_var(--color-lime)]`) or with opacity, as the Venta and Nuevo pedido pickers do.
- **Proveedores y compras** (`features/suppliers`): `ProveedoresPage` builds the rows of its three tables once (`buildOrderRows`, `buildPayableRows`, `buildSupplierRows`) and hands them to the tab components, which own only their search/filter/sort state and sheets; the chips beside the title follow the tab. An account payable is `vencida`/`hoy`/`proxima`/`vigente`/`pagada` against its due date (`DUE_SOON_DAYS` = 7), and a settled one opens `PayPayableSheet` read-only. Facturas opens on today: its period (`periodBounds`/`periodPhrase` in `invoices/lib/invoiceRows.ts`) is a preset, one chosen day or a from–to range, where an empty date never limits. A sale's row offers Corregir (`CorrectionModal`: quantities and prices editable, products added from the inventory through a search that suggests them as you type, and a preview of what will happen to the inventory and the caja before saving) and Anular (`VoidSheet`); an annulled one stays listed ("Anulada", struck through), has no actions and counts in no total.
- **Notices and the rest screen** (`features/notifications`): `buildNotices` (`lib/notices.ts`, pure) says what is pending — first, for the Administrador (the store's owner) only, the reminder of the system's monthly payment (due on `SERVICE_PAYMENT_DAY` = 13, shown from `SERVICE_REMINDER_DAYS` = 2 days before through the day itself, red, "si ya pagaste, omite este mensaje", a live `Countdown` to the end of that day in Bogotá; "Ya pagué", confirmed, stores that due day as `settings.servicePaid` — Administrador only, through `PUT /api/settings` — which hides it on every device and in the phone notifications until next month's) — then payables to suppliers (`buildPayableRows`' states: overdue or due today red, within 7 days orange), the Caja Menor still open from an earlier day, sales made without internet (rejected red, waiting orange), products out of stock (the Stock page's "sin stock") and at their minimum (`isLowStock`), fiados (orange once one is 30 days old) and orders sent but not received — using the existing rules, never new ones. `useNotices` gives each person only the modules their role opens (the need of that nav item; payables and orders only reach whoever has `proveedores.gestionar` anyway), and `NotificationCenter` (mounted once in `AppShell`) publishes them to `useNoticesStore` for the bell in `HeaderTools` (its count = red + orange notices) and the "Pendientes de hoy" sheet. That sheet opens by itself once per person, device and day (`mtp-daily-notices` in localStorage) when what they may see has been read (`hasSynced()`, the payables downloaded) and nobody is mid-sale (`safeToReload`), in a form, or typing. After 3 minutes without input the rest screen (`RestScreen`) covers the page: clock and pending items, the payables first and big. It is a portal, not a `<dialog>` (an idle till must still auto-update), never comes up over an open dialog or a save, and the input that wakes it only wakes it: a click on the overlay (not the press), a deliberate mouse move or the wheel, and keys swallowed at the window's capture phase until 400 ms pass without one, so a barcode reader's burst is dropped whole instead of half-read. **Phone notifications** (the Administrador only, even with the app closed): at the foot of that sheet `PushRow` turns them on for the device (`push.ts`: the browser's permission, then a Firebase Cloud Messaging token made through the app's own service worker — `getToken` with our registration — and `POST /api/push/token`, which only an Administrador may call and which sends a test one at once; `DELETE /api/push/token/:token` turns a device off, and "Cerrar sesión y borrar" does too). The tokens live in `private.push_tokens` (migration `20261014000000`, no browser access). Two scheduled Functions (`avisosPendientes` at 7:00, 17:00, 18:00 and 20:00, `avisosMediodia` at 12:20, America/Bogota — `PUSH_HOURS_LABEL` in `notices.ts` says the same to the user) run `sendPendingPush` (`server/domain/push.ts`): `pendingPush` reads the payables, orders, low/out products, the caja and `servicePaid` in one query and builds the message with the same `buildNotices` + `pushMessage` (nothing is sent when nothing is red or orange); only tokens of a currently active Administrador get it, the rest are deleted, and so are the ones FCM reports gone. FCM is sent with `firebase-admin` and the project's own credentials (no secret), as **data** (title, body, link), which `public/push-sw.js` (pulled into the generated service worker by workbox `importScripts`) shows; tapping one focuses an open app and tells it to open the sheet (a `postMessage`, no reload — a sale may be half done) or opens `/?avisos=1`. The installed .exe/.apk and `npm run dev` have no service worker, so no notifications there; an iPhone gets them only from the app added to the home screen.
- **A save never looks idle**: `src/api/client.ts` locks the button that was just clicked for as long as a write (POST/PUT/DELETE) is in flight — `button[data-loading]` in `index.css` swaps its icon for a spinner and it can't be pressed twice — and counts the writes in `useBusyStore`, which `BusyBar` (top of `AppShell`) shows as a thin moving bar after a quarter of a second. No handler has to opt in; what the app does by itself (the heartbeat, a PIN check, signing out: `BACKGROUND` in `client.ts`) is exempt, and so is reading. A handler that waits on something else first (a PDF being made) keeps its own `busy` state, as `ShareReceiptPanel` does.

Native `<dialog>` is the standard modal primitive (backdrop, Escape, focus trap, top-layer stacking all come free) — don't hand-roll a new overlay/portal for a modal. Clicking the backdrop deliberately does nothing but nudge (`src/shared/lib/backdropNudge.ts`), so a mis-tap never throws away a half-filled form: every `Modal`/`BottomSheet` needs its own visible Cancelar/Cerrar (X) — Escape still closes. A dialog taller than the screen shrinks its content up to 20% (`useFitHeight`, applied by `Modal`/`BottomSheet`/`PinModal`) instead of showing a scrollbar, so design forms to fit about 600px of height and keep long lists in their own scrolling area. The app must work from the keyboard alone (not every till has a touch screen): `Modal`/`BottomSheet` mount their content only once `showModal()` has run (`useShowDialog`) — a field's `autoFocus` focuses it as it mounts, which did nothing inside a dialog that wasn't showing yet, so every sheet used to need a click on its field before typing — and Enter in a text field presses the dialog's button marked `data-enter` (`lib/enterSubmits.ts`; a disabled button does nothing): mark the main button of any new form. A widget with its own keypad must also take the physical keys: the calculator (F9 opens it from Venta; digits, + − * /, Enter, Backspace, Esc) and the weight sheet's quantity field do, and anything that types by itself marks its root `data-keys-owner` so the barcode reader (`useHidScanner`, which reads fast keystrokes anywhere outside a field) leaves those keys alone.
- **Roles and permissions** decide what each person working at the store sees and does. The catalog lives in `src/shared/lib/permissions.ts` (pure, also used by the server): `PERMISSION_GROUPS` (each permission has a label, a one-line hint and `requires` — granting it grants those, revoking one of those revokes it), the fixed `Administrador` (every permission, plus the only access to Configuración: the `'admin'` need), the editable built-ins `Supervisor`/`Cajero` and custom roles stored in `settings.roles` (always read through `resolveRoles()`/`sanitizeRoles()`, never raw), and `settings.access` (`sanitizeAccess()`: only the inactivity sign-out). A `usuario.role` is a role id; a deleted role grants nothing. The nav (`BottomNav`/`DesktopTabs`) lists only the modules the role opens; a module reached by URL anyway shows `ModuleGate`'s "sin acceso" panel (Volver a Venta / Cambiar de usuario).
- **Who is working** is `useSessionStore().operator`: the person whose account is signed in, as the server said (`src/features/pin/counterSession.ts`: `refreshCounterSession`/`startCounterSession` bind the session and renew it, `counterApprove` records a PIN approval). The owner's account is `{ id: 'owner', roleId: 'admin' }`; a user's is their `usuarios.id`. Until the server answers, the app draws the screens from who this account was the last time on this device (`mtp-operator` in localStorage — a convenience only; `serverReady` stays false, so no secret data is downloaded, and the server decides everything). `useSessionGuard` (AppShell) binds at start and every minute (a 401 first retries once with a renewed token; 401/403 signs out and the login says why — lost access, or "sign in again" for sessions from before the switch), follows admin edits (renamed/new role → applied; deactivated → confirmed with the server and signed out), signs out after `settings.access.idleSignOutMinutes` without input on any tab (also when the app is reopened after that long), and feeds `setSecurePerms`. The server signs sales (`sellerId`/`sellerName`), cash operations and cierres with whoever is signed in on the session — never with what the browser says.
- **The single permission mechanism is `usePermission()`** (`src/features/pin/usePermission.ts`) — don't invent a second one. `can(need)` answers for whoever is working — to decide what to show; the server applies the same catalog to what actually happens. For a step they can't take, `requirePermission(need, title, subtitle)` / `authorize()` ask for the PIN of someone allowed, which records a server-side approval for that one step on this session **without** changing who is signed in (a supervisor approving a cashier's discount; `authorize()` returns who approved); what only the Administrador does (`'admin'`) can't be approved — it needs an administrator's own account ("Cambiar de usuario"). A PIN that's right but lacks the permission gets a named refusal and doesn't count as a wrong guess. Things the role may not see simply aren't offered (nav items, the purchase-price column and its Excel/CSV exports in Stock). When adding something sensitive: put the data where RLS guards it, check the permission in the route, and gate the UI with these — purchase prices (`costos.ver`), profits and inventory value (`ganancias.ver`, which includes `costos.ver`), the cash ledger and blind count (`caja.verEsperado`: without it the open/close sheets hide the expected cash and the difference, and the server's answers and errors leave them out too). `ventas.verTotales` only hides the day's totals on screen: whoever enters Facturas still sees each sale.

### Cash-register domain specifics

`Sale` (`src/types/sale.ts`) carries `chargeOverride`, `amountReceived`, `changeGiven`, and `roundingAdjustment` as explicit, separate fields from `subtotal`/`discount`/`total` — never fold a rounding or tender adjustment into those base fields, the UI (`CartPanel`) and reports rely on them staying transparent and separately inspectable. A cash charge can't be confirmed until the cashier has said what the customer paid with: in the Cobrar sheet the bills add up (each press adds its value), "Borrar" clears and "Exacto" is the total, and the figure starts from 0 every time the sheet opens; `CartPanel` keeps the button off and `charge()` in `useFinalizeSale` refuses too. The server does not insist (`amountReceived` stays optional there), because a sale made without internet or by an older screen must still be saved.

**Discounts are money on one product**: the Cobrar sheet's tag button opens `QuickDiscountModal` — pick a line of the cart and type how much comes off it (no percentages; never more than the line is worth). It is stored as `CartItem.discount` (money, for the whole line), and the sale's `discount` is their sum (`manualDiscountOf` in `src/shared/lib/discounts.ts`): that is where every total comes from, and the line says which product it went to. The server (`cleanLineDiscount` in `server/domain/sales.ts`) refuses a line discount above the line or a sum above the sale's discount, and any discount needs `ventas.descuentos` (or an approval); a correction keeps each line's discount (cut to what the line is worth now) without recalculating the sale's, and a sale made without internet keeps them and notes what doesn't add up. The receipts show it everywhere — on the till, in the text/PDF, the e-mail and the WhatsApp page — next to the product. A sale's profit (`Sale.ganancia`) is what was charged minus what the goods cost, so a discount (or the rounding of a cash charge) comes off it; sales made before 2026-10-13 kept the old figure (price minus cost, before discounts).

**There is no loyalty program**: no points, no levels (Bronce/Plata/Oro) and no automatic discount for customers — they were removed on purpose (2026-10-13), so don't bring them back. A customer is a name with their contact data and what they have bought: total spent (`getSpent`, annulled sales left out), number of purchases, last purchase, favourite product.

**Transfers say which account they came into** (`src/shared/lib/transferAccounts.ts`: Nequi and Bancolombia — Ahorro a la Mano is a Bancolombia account, so it is that option's caption — with the entities' own icons, the ones their websites use, in `src/assets/banks`, drawn by `AccountIcon`/`AccountPicker`): the Cobrar sheet won't confirm a transfer until one is picked (it starts empty at every charge), and a fiado payment by transfer asks too. The account is kept on the sale (`transferAccount`), on a fiado payment (`FiadoPago.account`) and on the Caja Mayor movement (`CashMovement.cuenta`; corrections, annulments and the refund of payments keep it). `computeDayAggregate` adds `transferBreak` — transfer sales plus transfer fiado payments minus refunds, per account, `sin` = didn't say — which Reporte, Reporte X, the Cierre Z sheet and the archived `Cierre.transferBreak` show; the Cierre also marks those Caja Mayor movements closed (`transferMovementsDay`) so a day closed twice doesn't count them twice. The server doesn't insist on the account (older screens and sales made without internet still save; the latter get a review note), and a made-up account is a 400.

Cierre Z (day close) is **non-destructive**: sales and cash movements get `closedInCierreId` stamped on them, they're never deleted. Any report/aggregation logic must filter on that field rather than assuming "current day close = current data". It is also how the Caja Menor workday ends: the expected cash is the ledger balance, the gap against the counted cash becomes an `ajuste_arqueo` movement, and an optional transfer to the Caja Mayor happens in the same transaction. The server computes the whole day's aggregate itself (`closingAggregate`) — the browser only sends the counted cash, the transfer and notes, since whoever closes may be counting blind.

**The Caja Mayor has an eye** (Cajas, on its card; `useMayorStore`, `src/features/cash/mayorEye.ts`): closed — how it starts, every time the app is loaded and after every sign-out — its balance, the transfers received today and its movements are hidden, and nothing can be moved into or out of it from Cajas (Trasladar a Caja Mayor, Registrar egreso, Ingreso, Reponer Caja Menor answer with a notice) nor into it by the Cierre Z (its "Trasladar fondos a Caja Mayor" box stays off); open, all of that works. Opening always asks a PIN (`counterApprove` for `caja.gestionar`: the person working or anyone allowed, checked by the server, and the factory 1234 never opens it); closing is one click. It is a screen lock for whoever stands at the till, in memory only — not an API lock: the permissions of the routes are what the server enforces — and the supplier sheets (paying or receiving an order) just show •••••• instead of the Mayor's balance while it is closed.

**Cajas are a ledger, not stored balances** (`cashMovements`, `src/types/cash.ts`): a caja's balance is always the sum of its movements (`balanceOf` in `src/shared/lib/cash.ts`), amounts are always positive with a `direction`, and nothing is ever edited or deleted — corrections are new movements. Caja Menor = the drawer (cash sales, fiado collections, petty expenses; a `cashSessions` row per opened workday); Caja Mayor = safe/bank (receives transfers, pays payroll/rent/utilities/suppliers). Money lands where it physically is: cash sales and cash fiado payments go to the Menor, bank-transfer ones to the Mayor (`medio: 'transferencia'`); fiado sales and forgiven debts move nothing. The first opening ever is the start of the books (base inicial of the Menor + optional saldo inicial of the Mayor) — sales from before the cajas existed are deliberately not back-filled. Spending from a caja is rejected when its balance is insufficient.

**Selling prices**: a product has up to three. `price` is Precio 1 — what every screen shows and what Margen is worked from — and `price2`/`price3` are optional extras (absent = not set, never 0; set in the product's form, shown as the Precio 1/2/3 columns of Stock). `src/shared/lib/prices.ts` is the one rule (`priceOptions`, `sellingPrices`, `samePrice`). A product with more than one price gets a small tab beside its price on the cart line (`CartLine` → `PricePicker`; `setItemPrice` in the cart store acts on the active cart) to charge it at another; `WeightModal` keeps the picked price when a by-weight line is edited or added to. The sale route (`priceLines` in `server/domain/sales.ts`) charges a line at any of the product's current prices — no permission needed, the Administrador registered them all — and refuses any other, so a made-up or removed price fails like a changed one. `server/routes/products.ts` (`extraPrice`) keeps a stored Precio 2/3 when a request doesn't carry the key (a screen from before they existed must not wipe them by saving) and clears it on `0`/`null`. Exports, the import template and imports read "Precio 1" (also the old "Precio Venta"), "Precio 2" and "Precio 3".

**A product's code can be changed** (the code field of the product form, also filled by a barcode scan while the form is open): `PUT /api/products/:code` with a different `code` in the body goes through `renameProduct` (`server/domain/productCode.ts`), one transaction that writes the new row, deletes the old one (so every device is told, and the cost row follows by its trigger — the stored cost is carried over even to someone who can't see costs), updates the package ↔ loose-unit link, rewrites the `code` of every sale item and of the lines of purchase orders still `borrador`/`pedido` (received ones are history), and signs a `cambio_codigo` entry in the audit log; the profit rows don't change. `assertCodeFree` (also used when creating) refuses a code another product has — case-insensitively, scanners don't tell them apart — or that a package reserves for its loose unit. A key that is deleted and used again must not stay in `deletions` (`reviveKey`: creating, importing or renaming into a code clears its old deletion note), or a device that syncs late would replay the old deletion after downloading the new row and lose it. A body without `code`, or with the stored one, is no change (an older screen).

**Sale corrections and stock writes**: `correctSale` recomputes the total as items − discount **+ the checkout's `roundingAdjustment`** (dropping it moved the caja by the rounding on a correction that changed nothing) and refuses to sell more than there is, like a sale (`Stock insuficiente`). `correctSale` and `voidSale` (`POST /api/sales/:id/void`, the same `facturas.corregir` permission) move the inventory with ONE rule, `stockEffect` (`src/shared/lib/saleStock.ts`, which the screens also use to preview it): per product the old lines give their units back and the new ones take theirs, written in one `setStocks`. A correction takes inventory products only — chosen from the list, never typed free; the browser's `isFree` is never trusted, a free line stays only if the sale already had that very line — needs a reason, can't empty the invoice (that is Anular) and can't take a fiado's total under what was already paid. An annulment keeps the row (`voided`, `voidedAt/By/Reason`, audit entry `anulacion_venta`), puts the units back, takes the sale's total out of the caja it went into (`ajuste_venta` out), gives back the fiado payments that were collected (`egreso`, from the caja each came into; forgiven ones move nothing), removes the shared-receipt link (a correction refreshes it) and is idempotent. Every aggregate leaves voided sales out (`computeDayAggregate`, `getSpent`, `groupFiados`/`getFiadoDebt`, the customer screens, Reporte's fiado figures, Facturas' totals): a new place that sums sales must skip `voided` too. The product form only sends `stock` when its field was touched (`updateProduct(…, { keepStock })`) and `PUT /api/products/:code` keeps the stored stock when the key is absent — the figure a form loaded is stale after any sale — and signs an `auditLog` entry when the stock does change through it; an import that replaces stock logs the same way. `POST /api/sales/finalize` has no idempotency key, so the browser guards instead: `useFinalizeSale` refuses a second charge of a cart whose sale is still being saved (a cold Function takes seconds, and the cart only empties when it answers).

**Purchasing** (`suppliers`, `purchaseOrders`, `payables`): stock only grows in `receiveOrder`, in the same transaction that books the payment (cash out of the chosen caja) or the account payable (due date = receipt day + the supplier's credit days). The old free-form `extras`/`purchases` tables were replaced by this. Day keys are computed in the store's timezone (`dayKeyOf` in `src/shared/lib/currency.ts`), never from UTC.

**Printing** (receipts, Reporte X) is thermal-paper HTML, not `window.print()` on whatever's on screen: `src/shared/components/PrintPortal.tsx` portals a dedicated 80mm view (with `PrintHeader`, the logo) to a sibling of `#root`, which `src/index.css`'s `@media print` rule (`#root { display: none }` + `@page { size: 80mm auto }`) hides everything else for. Add a `PrintPortal` block to any new printable dialog the same way — don't call `window.print()` without one, or the browser prints the on-screen dialog (rounded corners, backdrop, nav chrome and all).
**Sharing a receipt** (`ReceiptSheet` → Correo / WhatsApp, `ShareReceiptPanel`; anyone signed in may, a receipt carries nothing secret): the receipt is a `ReceiptData` (`src/shared/lib/receipt.ts`, shared with the server) — the same data the printed receipt shows and nothing else (no cost, profit or notes) — and the thermal text, the PDF (`receiptPdf.ts`), the e-mail and the public page all draw from it. The products are laid out as four columns — CANT. | DESCRIPCIÓN | P. UNIT. | VALOR — with the quantities in one straight right-aligned column, the price of one unit and the value of the line flush right, and a long name wrapping inside its own column: `ReceiptItems` (`shared/components`) draws it for the three HTML looks (the till's screen, the printed 80 mm slip, the WhatsApp page), `itemRows` in `receipt.ts` for the text and the PDF (`RECEIPT_COLS` = 45 characters, 7.5 pt Courier on the roll — keep every space, the PDF does not trim lines), and the e-mail has the same table. The **server builds it from the saved sale** (`server/domain/receipts.ts`), never from what the browser sends. *E-mail*: `POST /api/recibos/correo` (`server/routes/receipts.ts`, `server/mailer.ts` injected into `createApp` like `Accounts`; HTML escaped in `server/domain/receiptEmail.ts`; the PDF the browser made is attached only if it starts with `%PDF-` and is ≤ ~1 MB; 40 per account per hour, in memory; the SMTP conversation never holds a database connection). *WhatsApp*: `wa.me` can't carry a file, so `POST /api/recibos/compartir` stores the receipt in `private.shared_receipts` (migration `20261012000000`, no browser can reach it) under a random 128-bit code, one link per sale (sharing again refreshes it), valid 30 days (`RECEIPT_LINK_DAYS`; expired rows are deleted when another link is made) — and the message carries `<origin>/recibo/<code>`. The customer's page (`features/receipts/PublicReceiptPage`, API `GET /api/recibo/:id`, the one open route besides `/health`: 404 unknown, 410 expired, 429 over the 60 reads a minute it allows everybody together — it shares the till's few database connections — and 503, never the database's own error text, when it fails) builds the PDF on their own phone, so no PDF is ever stored; it never goes dark and is `noindex`/`no-referrer` (meta tags, the API's headers and `firebase.json`). `main.tsx` loads the app and that page as two separate lazy entries, so a customer's phone never downloads the app or its sign-in code. The panel opens `wa.me` with `window.open('')` **before** the first `await` (after it the browser blocks the pop-up) and falls back to the receipt as plain text if the link can't be made. An installed Android APK would need a native route for it; this PWA doesn't.


## Config notes

- TypeScript: bundler-mode resolution, `verbatimModuleSyntax`, extensionless relative imports, `noUnusedLocals`/`noUnusedParameters` enforced — `npm run build`'s `tsc -b` will fail on unused vars/params, don't rely on lint alone to catch that. The server has its own `server/tsconfig.json` (checked separately via `npm run typecheck:server`, not part of `npm run build`), with `erasableSyntaxOnly` (no enums or constructor parameter properties).
- Lint: `oxlint` (`.oxlintrc.json`), not ESLint.
- Tailwind 4 (`@theme` tokens in `src/index.css`, `.dark` class variant applied to `<body>` from `AppShell`'s theme effect) — no `tailwind.config.js`, tokens live in CSS.
- Colors come only from those tokens, never hex/rgba in components. The identity is the Plastimax F.R. brand palette. `lime` is the brand token and now holds the brand **blue** `#003d98` (primary buttons, active state) — the name is kept only to avoid churning ~230 usages; the other hues are statuses (`green` = money/income, `red` = alert/delete/debt only — never the primary/Cobrar action, `orange` = attention, `blue` = info, `purple` = secondary accent (credit, copied/sent confirmations)). `yellow` (`#fee436`) is only ever a **background** for promos/destacados, always with `text-on-yellow` (`#172033`, dark in both themes — never `text-txt`, which flips to light at night). Text on any other solid color is `text-on-solid` (white in light mode, near-black in dark). The nav chrome (where the modules are: `DesktopTabs`, mobile `Header`, `BottomNav`, plus `HeaderTools`) is the brand navy: `bg-nav`/`border-nav-line`, `text-nav-fg` active (with a `after:bg-yellow` underline on the desktop tabs), `text-nav-fg-dim` inactive, `bg-nav-hover` hover; the `nav-*` tokens stay blue in both themes (dark only lightens them a touch). Zones are separated by `border-br` hairlines and cards lifted with `shadow-xs` (the shadow color follows the theme through `--shadow-rgb`); `br2` is for the outline of controls, and the `grid` token (darker than both, set in `index.css` for each theme) is for the lines of every `DataTable` — its cells, rows, header and outer border — so the grid reads at a glance. `brand-deep` (`#001c5e`) is the navy, also available for gradients. Every text/background pair is kept ≥ WCAG AA 4.5:1 in both themes.
- The banknote photos on the checkout's quick-cash buttons are shrunk copies in `src/assets/bills` (mapped by `src/shared/lib/bills.ts`; the originals stay in the git-ignored `MIOS/bills`). `vite.config.ts` precaches `.jpg` so they also show offline.
- The store's logo and the app icons are shrunk copies of the transparent original in the git-ignored `MIOS/icon`: `src/assets/logo.png` (login) and `logo-sm.png` (the corner of the chrome, via `StoreBrand`, which shows the logo instead of the configured name — receipts, the Reporte X and the exports still print the name), plus `public/icons/` (`logo-192/512` for "any", `logo-maskable-192/512` on white with the logo inside the safe circle, `apple-touch-icon`, `favicon-32`). The icon files got new names on purpose, so browsers don't keep the old favicon cached.
- `legacy/` is the old app's static assets (kept for reference/migration, not part of the build). The old single-machine SQLite database (`server/data/tienda.db`, git-ignored, only on machines that had it) was copied into Supabase once, on 2026-10-02, and its importer was deleted afterwards; nothing reads that file anymore.
- `npm run lint` exits 0 but has a standing baseline of React-compiler warnings (`react(refs)`, `react(set-state-in-effect)`, and `react(incompatible-library)` for `useVirtualizer` in `DataTable`): judge new code by whether it adds warnings, and treat `npm run build` + `npm run typecheck:server` as the real gate.
- To look at a screen without signing in (a script can't): put a throwaway folder in the repo root (`index.html` + `main.tsx`, served by `npm run dev`) that fills Dexie (`db.products.bulkAdd`) and the secret tables (`putSecure('payables', rows, true)`), calls `useSessionStore.getState().confirm({ id: 'owner', name: '…', roleId: 'admin' })` and renders the page, then screenshot it with `chrome --headless=new --screenshot=… --virtual-time-budget=9000 --user-data-dir=<a new folder each run>` (a reused profile left IndexedDB stuck and the page blank). Delete the folder afterwards — never commit it. A page that imports `src/api/*` can't run under `tsx` (it reads `import.meta.env`): bundle a pure-logic script with `esbuild --bundle --platform=node --define:import.meta.env=…` instead.
- `scripts/offline-check/` is also how to exercise anything that needs a signed-in app without touching production: `apiServer.ts` is the real API on an in-memory PGlite with controls to cut, hang, delay or fail the connection (`POST /__test/mode`: `down`, `hang`, `status` with a JSON/`down`/HTML body or a stalled one, `lostAnswer`, `delay`) and `GET /__test/state` (stocks, sales and how many times each route was called), `fakeSupabase.ts` stands in for Supabase Auth/PostgREST/Realtime, `servers.mjs` builds the app against them (`buildApp`, optionally `packaged`) and `cdp.mjs` drives headless Chrome (evaluate, wait, screenshot, `setNetwork(offline)`, `newTab()` for a second tab of the same profile). The ports are 3002/3003/5174/4180 (`OFFLINE_CHECK_*_PORT` to change them), so they don't collide with `npm run server` and `npm run dev`.
- Windows checkout with `core.autocrlf=true` and no `.gitattributes`: older files are CRLF in the working tree, newer ones LF. A multi-line `Edit` doesn't match the CRLF ones — normalize `\r\n` in a small script (and restore it) instead of rewriting the whole file, so diffs stay small.
